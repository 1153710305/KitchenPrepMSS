# 食堂备菜管理和统计系统 (V2.5.0)

本项目是一个专门针对校园、机关或大中型食堂食堂设计的“日矩阵记账、深度财务统计及 AI 膳食配餐辅助决策”全功能管理系统。它完全采用 **TypeScript + React + Express Full-Stack** 架构设计，保障流畅的人机交互以及高密度的操作性能。

## 🌟 核心功能特色

1. **多级表格人群管理（级联决策根）**：
   - 包含以 **教师备餐**、**幼儿备餐**、**低年级备餐** 和 **高年级备餐** 等组成的独立核算客群。

2. **多维食材大类管理（记账大品类）**：
   - 可在 **蔬菜**、**粮油**、**调料**、**肉类**、**低耗品**、**水果** 等品类间动态抉择。
   - 特设 **合计汇总表**：一键生成全类别当期资金统计、各品类采购总金额比例及详细耗资说明。

3. **双重高性能编辑视图**：
   - **EXCEL 日历总矩阵**：复现经典的日历横轴大宽表，横向是 1号 到 31号 (根据月度自适应天数)，纵向是细分食材（例如：土豆、柿子、大黄油等）。每天下方含有 **数量**、**单价**、**金额** 纵队（金额由公式 `数量 * 单价` 自适应动态生成），首列冻结，支持批量一整列克隆单价调价。
   - **单日聚焦卡片（推荐模式）**：专为非宽屏或高频录入人员设计。支持在横向日期轴上点击指定天（如 15日），无需横向拖曳即可在垂直卡片内微调当天所有菜品的数量与价格，带来极佳的用户体验。

4. **实时财务图表看板**：
   - 引入 **Recharts** 绘制日消耗开支平滑面积图，辅助控制超预算。
   - 精细渲染食材大类采购资金配比条状占比，清晰揭示成本结构。
   - 显示全月度总开销、品类覆盖密度、日均耗资、以及 **重点监控高开销食材 Top 5 榜单**。

5. **AI 智能营养调配与控本审计**：
   - 在服务端深层整合 **Gemini-3.5-flash** 与 `@google/genai` 统一接口。
   - 默认提供 **在线打字流式 (Chunk-by-Chunk SSE Stream)** 与 **传统常规普通 API** 双重模式，一键切换。
   - 提取当期采购高频项目轻量级序列化传递给 AI，由专业食堂膳食调配师与财务管控专家多维度反馈“膳食平衡与人群营养诊断”、“食堂控本替代路径”和“采购冷链储存安全指导”，并给出膳食健康指数。

6. **行政管理与控制配置后台 (Diagnostics Admin)**：
   - 具备功能强大的受众人群一级分类、食材分类二级品类的添加、更新、删除即时数据级联核对 (CRUD) 面板。
   - 搭载进程总线实时嗅探和日志审计器，开发人员和行政管理人员可在此处单一入口对食堂系统、安全及离线缓存进行全量诊断。

7. **离线备份与迁移**：
   - 支持全账目一键打包导出为本地 `.json` 数据备份包，并配置了安全性的校验导入功能，实现零流失记账。
   - 每张单大类表支持一键一键导出为 Excel 可直接识别的 UTF-8-BOM 开源 CSV 总格。

---

## 🛠️ 技术底盘与软件架构

- **前端技术**：React (V19) + TypeScript + Tailwind CSS (V4) + lucide-react (图标)
- **绘图引擎**：Recharts
- **富文本解释**：React-Markdown (用于渲染 AI 的结构化深度分析)
- **后端服务**：Node.js + Express (统一端口 3000 ，容器入口防沙箱过滤)
- **编译工具**：Vite + esbuild (将 Express 静态集成编译至单个 cjs 自立服务，契合前后端完美分离的趋势需求)

### [V1.3.1] - 2026-06-23 (核心响应性 Bug 修复)
- **底层不可变数据(Immutable)更新机制升级**：
  - **现象定位**：修复了用户在“Excel日历总矩阵”和“单日聚焦卡片”中无法修改食材数量与单价，以及“点击新增项没有反应”的严重系统响应性阻滞缺陷。
  - **根源剖析**：由于之前底层 `PrepReportService` 状态服务采用的是 Mutable（可变突变）形式的深层级对象属性修改（如直接 `report.items.push()` 或直接修改深层 `dailyData[day]` 指标），且修改单元格处省去了分发广播事件，导致 React 内存引用没有产生变化，进而触发不了 UI 依赖项的 `useMemo` 重新计算及受控组件值的有效回刷。
  - **重构方案**：对 `addPreparedItem`、`updateCell`、`deletePreparedItem`、`batchUpdatePriceCol` 以及 `clearAllMonthlyCells` 等全部涉及多维底册突变更改的方法进行深度重构，完全转向不可变(Immutable)对象及数组克隆模型。每当用户产生单个数字击键、单价一键同步或新增菜品行为，均会创建全新引用结构的 reports、report 树并全速持久化分发给监听器，完美驱动 React 高灵敏重绘刷新，使得输入编辑与新增操作即时生效、毫无卡顿！

## 🚀 系统部署及数据安全手册

由于本项目主要服务于教育单位，保密级别高、且数据绝对安全性是首要原则。系统经过专门架构设计，既支持托管在腾讯云（使用私有对象存储隔离数据），也支持在一台学校本地的普通 PC 电脑上单机运行。

### 一、 本地单机部署方案（适合独立电脑运行，数据完全保密）

本地部署旨在让学校食堂管理人员或库管在自己电脑上单机操作，数据全部保存在本地硬盘的 `data/db.json` 中，不受浏览器缓存清理或网络断网的影响。

#### 1. 运行环境准备
- 在部署的电脑上下载并安装 **Node.js**（推荐选择最新 LTS 版本，下载地址：[Node.js 官方网站](https://nodejs.org/)）。

#### 2. 程序部署步骤
1. 将本项目源码文件夹复制到目标电脑的某个非系统盘目录下（例如 `D:\KitchenPrepMSS`）。
2. 在该目录下，使用管理员权限打开命令行（CMD 或 PowerShell），执行以下命令安装依赖：
   ```bash
   npm install
   ```
3. 在根目录创建或编辑 `.env` 配置文件，确保包含以下配置项：
   ```env
   # 首页登录密码与管理密码
   VITE_LOGIN_PASSWORD="guest"
   VITE_ADMIN_PASSWORD="admin"

   # 启用本地数据存储
   STORAGE_TYPE="local"
   LOCAL_DB_PATH="data/db.json"
   ```
4. 执行编译命令，生成静态生产文件包：
   ```bash
   npm run build
   ```

#### 3. 制作“一键双击启动”脚本（防非技术人员误操作）
为了方便学校工作人员每日开箱即用，避免输入命令，可在项目根目录下新建一个名为 `双击启动系统.bat` 的文本文件，并将以下内容复制进去保存：
```bat
@echo off
:: 设置字符集为 UTF-8 防乱码
chcp 65001 > nul
title 食堂备餐与台账管理系统

echo ===================================================
echo   食堂备餐管理与统计系统正在启动中...
echo   说明：启动成功后会自动打开浏览器，请勿关闭本命令行窗口！
echo ===================================================

:: 延迟 2 秒自动呼起默认浏览器访问系统
start http://localhost:3000

:: 运行 Express 服务端
npm run dev

pause
```
之后，操作人员只需双击 `双击启动系统.bat`，即可自动启动系统并弹出浏览器页面开始使用。

#### 4. 本地数据安全与快照恢复策略
- **本地主数据文件**：保存在 `data/db.json` 中。
- **自动备份防误删**：当每次修改账目或出入库记录失去焦点保存时，系统除了更新 `data/db.json` 之外，还会在 `data/backups/` 目录下自动生成一个带有精确时间戳的快照文件，形如：`db_20260630-162000.json`。
- **超期清理**：为了防止备份膨胀，后端会自动将备份快照控制在最近 30 次，超出 30 个的历史老备份会被自动轮换清除。
- **数据恢复方案**：如果不小心在管理配置后台中误清空了账目，或者修改错误想要找回，可以直接在本地 `data/backups/` 下找到历史某时刻的快照，将其更名复制替换掉 `data/db.json` 即可完成完全恢复，或者通过管理配置后台的快照回滚功能一键物理回滚。

### 二、 腾讯云端部署方案（使用腾讯云服务器 + COS 对象存储）

若教育单位有多个校区需要联网协同录入，或希望数据存放在云端且定期异地冷备，可将系统部署至腾讯云。

#### 1. 腾讯云 COS 对象存储准备
1. 登录腾讯云控制台，进入 **对象存储 (COS)** 控制台。
2. 新建一个存储桶（Bucket），如命名为 `kitchen-prep-1234567890`，所属地域选择就近地域（如 `ap-guangzhou`）。
3. 访问权限务必设置为 **私有读写**（因包含财务和就餐人数敏感信息，绝对不能公开）。
4. 在腾讯云访问管理（CAM）控制台，获取该账号的 `SecretId` 和 `SecretKey`。
5. **重要安全建议**：在存储桶的安全设置中开启 **版本控制（Versioning）**。开启后，即使代码或人为误删了 COS 中的 `db.json`，COS 也会保留其所有历史覆盖版本，可在腾讯云后台随时拉回，确保数据资产绝对安全。

#### 2. 云端服务器配置
1. 购买一台腾讯云轻量应用服务器（或云服务器 CVM），系统选择 **Ubuntu/CentOS**。
2. 在服务器上安装 **Node.js** 和 **PM2** 守护工具：
   ```bash
   # 安装 Node.js (以 Ubuntu 为例)
   curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
   sudo apt-get install -y nodejs
   # 全局安装 pm2 进程守护管理器
   sudo npm install pm2 -g
   ```
3. 上传项目源码至服务器，并在项目根目录下执行 `npm install`。
4. 创建项目 `.env` 配置文件，填入对应的云端配置：
   ```env
   # 首页登录密码及管理密码
   VITE_LOGIN_PASSWORD="your_strong_login_password"
   VITE_ADMIN_PASSWORD="your_strong_admin_password"

   # 切换为腾讯云 COS 对象存储存储形态
   STORAGE_TYPE="cos"
   COS_SECRET_ID="你的腾讯云SecretId"
   COS_SECRET_KEY="你的腾讯云SecretKey"
   COS_REGION="ap-guangzhou"
   COS_BUCKET="kitchen-prep-1234567890"
   COS_KEY="production/db.json"
   ```
5. 编译代码：
   ```bash
   npm run build
   ```

#### 3. 云端生产环境启动与守护（支持手动端口与多服务隔离）

在多服务运行的云服务器上部署时，需要配置独立的运行端口，并通过 Nginx 进行反向代理与域名映射，确保各服务之间互不影响：

##### (1) 手动修改/指定部署端口
后端服务默认监听 **3000** 端口。如果该端口已被服务器上其他服务占用，您可以通过配置 `.env` 环境变量中的 `PORT` 参数，或者在启动时直接注入环境变量来手动更改端口：
- **方式 A：在 `.env` 中指定**（推荐，便于管理）：
  ```env
  PORT=8085  # 手动将系统部署端口修改为 8085
  ```
- **方式 B：命令行启动时临时注入**：
  ```bash
  PORT=8085 node dist/server.cjs
  ```

##### (2) 灵活选择是否启用云端 COS 对象存储
系统支持在云端直接读写本地 JSON 文件，也支持使用腾讯云 COS。通过调整 `.env` 配置文件中的 `STORAGE_TYPE` 来开启/关闭：
- **不使用对象存储（使用本地单机 JSON 文件）**：
  ```env
  STORAGE_TYPE="local"
  LOCAL_DB_PATH="data/db.json"  # 数据将以 JSON 文件形式存储在服务器项目根目录的 data 文件夹下
  ```
- **使用云端对象存储（数据完全托管到腾讯云 COS）**：
  ```env
  STORAGE_TYPE="cos"
  COS_SECRET_ID="您的腾讯云SecretId"
  COS_SECRET_KEY="您的腾讯云SecretKey"
  COS_REGION="ap-guangzhou"
  COS_BUCKET="你的存储桶名称-1234567890"
  COS_KEY="production/db.json"
  ```

##### (3) 如何使用域名访问与 Nginx 反向代理（多服务无冲突共存）
为了使用域名访问系统，且不影响服务器上其他正在运行的服务，建议使用 **Nginx** 作为统一的网关，通过配置反向代理（Reverse Proxy）和虚拟主机（Virtual Host）将特定子域名转发至食堂系统的对应端口。

1. **配置 DNS 解析**：
   在您的域名服务商控制台（如腾讯云 DNS Pod），为系统添加一条 `A 记录` 或 `CNAME 记录`，将子域名（如 `kitchen.yourdomain.com`）指向您的云服务器公网 IP。

2. **配置 Nginx 虚拟主机 (避免服务冲突)**：
   在服务器的 Nginx 配置目录（通常为 `/etc/nginx/sites-available/` 或 `/etc/nginx/conf.d/`）下为食堂系统建立独立的配置文件（例如 `kitchen.conf`），加入以下配置：
   ```nginx
   server {
       listen 80;
       server_name kitchen.yourdomain.com; # 绑定您的食堂系统专属访问域名

       # 调高 Nginx 上传限额，防止备份包导入时因 Payload 过大被拦截 (同 Express 的 50MB 限制对齐)
       client_max_body_size 50m;

       # 开启 Gzip 压缩，加速老旧 Win7 客户端大矩阵的加载速度
       gzip on;
       gzip_types text/plain text/css application/json application/javascript text/xml;

       location / {
           proxy_pass http://127.0.0.1:8085; # 对应您在系统 .env 中手动指定的 PORT 端口
           proxy_http_version 1.1;
           proxy_set_header Upgrade $http_upgrade;
           proxy_set_header Connection 'upgrade';
           proxy_set_header Host $host;
           proxy_cache_bypass $http_upgrade;
           
           # 转发真实客户端 IP 供后台审计日志留存
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
       }
   }
   ```
   *通过这种域名配置，即使服务器上运行着数十个其他 Web 网站或微服务，只要它们的 `server_name` 域名不同，或者监听不同的本地端口，Nginx 就能在入口处精准路由，**各服务之间在运行端口与流量通道上实现了 100% 物理隔离，互不干扰**。*

3. **测试并重载 Nginx 规则**：
   ```bash
   sudo nginx -t          # 检查配置文件语法是否正确
   sudo systemctl reload nginx # 重载 Nginx 服务使配置立即生效
   ```

4. **开启 HTTPS 安全访问 (可选但强烈建议)**：
   由于食堂包含敏感的就餐和采购成本数据，建议使用免费的 Let's Encrypt 工具为域名部署 SSL 证书：
   ```bash
   sudo apt-get install certbot python3-certbot-nginx
   sudo certbot --nginx -d kitchen.yourdomain.com
   ```

##### (4) 云端生产环境 PM2 守护启动命令
在 `.env` 完成端口和存储选择、并由 Nginx 配置好反向代理后，执行以下命令在后台独立守护启动：
```bash
# 使用 PM2 启动生产环境并命名为 kitchen-prep-system
pm2 start dist/server.cjs --name "kitchen-prep-system"

# 固化 PM2 运行列表并设置服务器开机自动拉起进程
pm2 save
pm2 startup
```

### 二、 客户端显示异常排查与调优方案 (解决字体、颜色、Emoji、显示不全问题)

系统已经通过 `index.html` 注入了自动重绘脚本与全局字体回退渲染，以实现老旧系统的平滑兼容：

#### 1. 字体锯齿与难看宋体问题
- **现象**：由于 Win7 缺少现代字体，系统界面默认会 fallback 到 `SimSun` (宋体)，在高分屏下字形极小且带有明显灰色锯齿。

#### 2. Emoji 图标显示为黑白方块、空心框或不显示
- **现象**：Windows 7 操作系统原生不带任何彩色 Emoji 字符集（如 Segoe UI Emoji），会导致前台受众人群表情（👶, 🎒, 🏫 等）显示为难看的分裂方块。
- **已部署解决方案**：
  - 系统引入了 **Twitter Twemoji (v14.0.2)** 的全局监听转换组件。
  - 页面初次加载或 React 动态进行局部 DOM 更新渲染时，底层脚本会自动识别原生 unicode emoji，并使用 CDN 上的**高精 SVG 矢量图片**在 0.05 秒内直接在页面中进行替换（生成带有 `.emoji` 样式类的图片），完美还原饱满亮丽的扁平化彩色图标外观。
  - **离线环境提示**：若部署在完全没有公网的局域网内部，CDN 地址可能无法访问。此时管理员可以在管理后台将一级受众或餐卡的外观图标由 Unicode 字符直接修改为**常规文字**，从而在根源上规避显示黑白方块的问题。

#### 3. 页面部分侧边栏或大矩阵表显示不全、遮挡或滚动条失效
- **现象**：老旧浏览器对 Tailwind CSS 的某些现代盒模型（如 `flex-1` 或自适应滚动机制）渲染存在偏差，导致表格内容被切断、看不见右侧或无法往后滚动。
- **已部署解决方案**：
  - 系统对全局滚动条设定了 `-webkit-scrollbar` 精简滚动轨迹，为 Windows 7 下的低清显示器腾出空间，防止其侵入原本的容器布局。
  - 系统已为台账样式一增加了 `min-w-[1380px]` 并外裹 `overflow-x-auto` 容器，在任何老旧显示器上均会稳定显示出底部的原生横向滚动条，可直接向右滑动查看“索证、供货商、保管员”等完整要件，彻底解决“页面显示不全”的问题。
  - **浏览器推荐**：严禁使用 Windows 7 自带的旧版 **Internet Explorer (IE)** 浏览器进行访问。推荐下载并安装 **Google Chrome** 现代浏览器（支持 Win7 的 Chrome 109 最终版本）或 **360安全浏览器（切换为极速内核模式）** 以获得最佳渲染效果。

### 2026-07-01 - [V5.10.0] 废除本地浏览器 LocalStorage 缓存，升级为准实时多端心跳同步架构
- **原因分析**：
  此前系统采用「本地改 LocalStorage -> 防抖全量覆盖云端」设计。在多浏览器多用户高并发使用时，由于各浏览器 LocalStorage 彼此隔离，会导致数据互相全量覆写并导致别人的录入丢失。

  1. **废除 LocalStorage**：从 [store.ts]、[ledgerStore.ts]、[rawMaterialDict.ts] 中物理移除所有 `localStorage.getItem/setItem` 的存取逻辑；
  2. **全局并行预载**：在 [App.tsx] 启动时通过 `Promise.all` 并行加载备餐、台账与原料大字典的初始化接口，防止各模块按需加载时因空内存上传而清空服务器文件；
  3. **一键内存提取器 (MemoryFetcher)**：由 SyncHelper 注册全局提取回调，在防抖同步时动态提取各 Store 最新的内存快照进行打包上传，规避 LocalStorage 媒介；
  4. **心跳校准对齐**：在首屏启动 `10秒静默心跳拉取器`，自动捕获云端服务器数据的变更，并以静默内存赋值方式刷新前台 React 视图，实现多浏览器视窗最终一致性。

### 2026-07-02 - [V5.34.0] 修复原料字典历史脏数据引发的 React 重复 Key 警告（黄瓜/土豆）
- **需求**：
  - 承接上一版本 V5.33.0 排查时登记的独立跟进任务：管理后台「原料字典管理」Tab 与「原料购销台账」录入模式下，控制台反复报出 `Encountered two children with the same key` 警告，涉及「黄瓜」「土豆」等原料名。

  - **数据源头去重**：在 [rawMaterialDict.ts] 新增 `dedupeByName()` 私有方法，按原料名对字典数组去重（同名保留最后一条，即视为更晚写入的最新数据），并在 `initDictFromServer()`（服务器首次加载）与 `setRawMaterialsDictInMemory()`（心跳轮询静默覆盖）两个唯一的批量赋值入口统一调用，确保内存中的 `items` 永远不含同名重复条目，从根源上让所有下游消费者（管理后台字典列表、台账录入合并、原料联想下拉框）都不再可能渲染出重复 key。

  - **持久化自愈**：`initDictFromServer()` 检测到本次加载发生了实际去重时，会通过新增的 `SyncHelper.runWhenInitialized()`（在 [syncHelper.ts] 新增的一次性回调队列机制）把清洗后的字典安全回写服务器——避免了在系统初始化安全锁解锁前直接调用同步导致请求被拦截丢弃的问题，实现历史脏数据的自动物理清除，无需人工介入清库。

  1. [LedgerPrintStyle2Consumable.tsx] 列结构从原先消耗品专属的 12 列（序号/物品名称/规格/单位/经销商/入库数量/入库日期/入库经手人/出库数量/出库经手人/当期库存/备注）整体替换为与购销总表（图一，[LedgerPrintStyle1.tsx]）同款的 10 列两行表头结构：物品名称/数量/规格/供货商/采购时间/采购员/检验员/出入库时间（入库/出库两个子列）/保管员；不再计算逐日库存结余（`stockByDay`），也不再展示单位列。
  2. 标题区同步改为与 [LedgerPrintStyle2.tsx]（[V5.61.0]）一致的布局：标题单独一行（保留下划线，与此前样式一致）；日期与受众台账名共用同一个 `justify-content: space-between` 的 Flex 行，日期在左、受众台账名被推到本行最右侧——由于该行宽度继承自标题所在的父容器（与标题等宽），受众台账名的最后一个字自然与标题的最后一个字对齐。`titlePrefix` 去掉末尾连字符，受众名不再拼接在标题文字里。
  3. 主表格保留 [V5.64.0] 已加入的线框统一样式（`.ledger-print-consumable-table` 限定作用域 `<style>`，纯黑 1px）与字号常量（标题 20px、日期/副标题 14px、表头 16px、数据行 14px），未受结构调整影响。
